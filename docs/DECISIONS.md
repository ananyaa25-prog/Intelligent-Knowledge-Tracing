# Decisions log

Each entry: decision — reason. Decisions were taken autonomously because the requester could not be asked.

- D1 Project root is `aiproj/aiproj` (the outer folder only holds it and `__MACOSX`). — Only that folder contains src/, server/, data/.
- D2 Created a project-local virtualenv `.venv` instead of installing into the global Python. — Global Python had no torch/fastapi/pytest; a local venv cannot break other projects on the machine.
- D3 `requirements.txt` is UTF-16 (a PowerShell `pip freeze`) and lacks fastapi, uvicorn, pydantic, pytest, httpx although the code imports them. These were installed into `.venv`; the file was left in its original encoding and they are listed in `requirements-serving.txt` (new, UTF-8). — Rule 7 says to use what is in requirements.txt; serving cannot run without these packages, and rewriting the original file's encoding is avoidable.
- D4 Git: initialised a repository, committed the baseline on `master`, work happens on `feature/adaptive-v2`. `core.autocrlf=false` locally so commits/reverts keep each file's exact line endings. — Restore point required by the brief; the machine's global autocrlf=true would otherwise rewrite line endings on revert.
- D5 The root `.gitignore` was a stray pytest-cache file containing `*` (ignore everything). Original kept as `.gitignore.pytest_orig.bak`; replaced with a real ignore list that excludes large data (data/raw, *.pkl, *.pt, the SQLite DB and the JSONL log). — Otherwise git would track nothing; the large/immutable data is never modified by this work.
- D6 Before any test run the DB and log were backed up with the SQLite backup API to `data/backups/`. — Rule 2.
- D7 Node.js is installed via WinGet but not on PATH; scripts locate it explicitly (see scripts/_env_util.py). `npm ci` was run in server/ (from the existing lockfile; package.json unchanged). — Needed to run the Node tests and the proxy.
- D8 Test isolation: added `tests/conftest.py` that copies the DB (SQLite backup API) and the JSONL log to a temp dir and sets `KT_DB_PATH` / `KT_LOG_PATH` before the serving code is imported. `db.py` and `inference_service.py` honour these variables only when set (no change otherwise). — Existing tests (e.g. test_e2e_adaptive) wrote test students into the real DB and log; the brief forbids that.
- D9 Pre-existing failing tests (15 pytest, 3 Node suites, all on the legacy fixed-quiz flow) were NOT modified or deleted. New behaviour is covered by new test files. "All existing tests must pass unchanged" is interpreted as "no test that passed at baseline may fail". — They failed before any change; editing them would hide that.
- D10 Opening the DB with the SQLite backup API checkpointed the WAL into the main file (the -wal/-shm files disappeared). Row counts were unchanged (48 students, 334 interactions). — Side effect of the mandated backup method; no data changed.
- D11 (pre-registered before running T1) Gate M uses the WORSE of two violation rates: (A) validation prefixes scored on the actual next skill (the brief's sample) and (B) the same prefixes scored on the 10 quiz topics (the topics the profile is actually computed for). — Safest choice: the profile is only trusted if the ordering holds both in-distribution and on the quiz topics.
- D12 Evaluation scripts import the service with a throw-away temp DB/log (scripts/_common.py) so they never touch the real DB.
- D13 Fallback (evidence-only) accuracy cut-offs 0.67 and 0.34 are treated as 2/3 and 1/3 inclusive (implemented as >= 0.665 and <= 0.34). — With 3 answers, 2 correct = 0.6667 would otherwise miss 0.67 by rounding, contrary to the evident intent.
- D14 Model policy "current level" = the topic's staircase state (`levels[topic]`, which starts at Medium and moves one step per answer from the level actually served). Candidates are that level and one step down/up; the model picks the one with predicted P closest to TARGET_P after guardrails. Ties prefer the current level, then the easier level. — Keeps the existing per-topic state and makes "one step" well-defined.
- D15 Guardrail G1 ("two consecutive wrong answers on the topic force one step down") restricts the choice to one level below the last served level on that topic. G2 removes Hard unless the topic's most recent Medium/Hard answer was correct (so a never-tested topic cannot jump to Hard).
- D16 With POLICY=model/random the served `predicted_p` is the prediction for the level actually served (re-scored); with POLICY=staircase it is unchanged (the topic-selection score). The staircase decision object still reports all three level predictions (one extra batched call) but the level rule is untouched (verified by a byte-identical trace test against the baseline engine).
- D17 Warm-up questions (first 2) and probes stay at Medium for every policy. — The model cannot predict before 2 answers; probes must stay comparable with the graph prediction made at Medium.
- D18 core5 mode: "total_questions=16" is read as the number of questions the student sees: 14 main questions on the 5 core topics (incl. the 2 warm-ups, max 4 per topic) + 2 probes on non-core topics. — Five non-core topics always remain unasked, so this total is deterministic.
- D19 `total_questions` for full10 = 15 + min(2, topics not yet asked); it can shrink from 17 to 15 during a session as topics get covered, and is exact once probing starts. The front end falls back to 15 if absent.
- D20 Decision reasons never mention whether an answer was correct. The Hard-lock reason states the rule ("Hard unlocks after a correct Medium or Hard answer on this topic"), which, like any level change, implicitly hints at past correctness; this is accepted and documented (SHOW_ADAPTATION_TOAST comment in app.js).

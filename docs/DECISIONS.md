# Decisions log

Each entry: decision — reason. Decisions were taken autonomously because the requester could not be asked.

- D1 Project root is `aiproj/aiproj` (the outer folder only holds it and `__MACOSX`). — Only that folder contains src/, server/, data/.
- D2 Created a project-local virtualenv `.venv` instead of installing into the global Python. — Global Python had no torch/fastapi/pytest; a local venv cannot break other projects on the machine.
- D3 `requirements.txt` is UTF-16 (a PowerShell `pip freeze`) and lacks fastapi, uvicorn, pydantic, pytest, httpx although the code imports them. These were installed into `.venv`; the file was left in its original encoding and they are listed in `requirements-serving.txt` (new, UTF-8). — Rule 7 says to use what is in requirements.txt; serving cannot run without these packages, and rewriting the original file's encoding is avoidable.
- D4 Git: initialised a repository, committed the baseline on `master`, work happens on `feature/adaptive-v2`. `core.autocrlf=false` locally so commits/reverts keep each file's exact line endings. — Restore point required by the brief; the machine's global autocrlf=true would otherwise rewrite line endings on revert.
- D5 The root `.gitignore` was a stray pytest-cache file containing `*` (ignore everything). Original kept as `.gitignore.pytest_orig.bak`; replaced with a real ignore list that excludes large data (data/raw, *.pkl, *.pt, the SQLite DB and the JSONL log). — Otherwise git would track nothing; the large/immutable data is never modified by this work.
- D6 Before any test run the DB and log were backed up with the SQLite backup API to `data/backups/`. — Rule 2.
- D7 Node.js is installed via WinGet but not on PATH; scripts locate it explicitly (see scripts/_env_util.py). `npm ci` was run in server/ (from the existing lockfile; package.json unchanged). — Needed to run the Node tests and the proxy.
- D8 Test isolation: added `tests/conftest.py` that copies the DB (SQLite backup API) and the JSONL log to a temp dir and sets `KT_DB_PATH` / `KT_LOG_PATH` before the serving code is imported. `db.py` and `inference_service.py` honour these variables only when set (no change otherwise). — Existing tests (e.g. test_e2e_adaptive) wrote test students into the real DB and log; the brief forbids that.
- D9 Pre-existing failing tests (15 pytest, 3 Node suites, all on the legacy fixed-quiz flow) were NOT modified or deleted. New behaviour is covered by new test files. "All existing tests must pass unchanged" is interpreted as "no test that passed at baseline may fail". — They failed before any change; editing them would hide that.
- D10 Opening the DB with the SQLite backup API checkpointed the WAL into the main file (the -wal/-shm files disappeared). Row counts were unchanged (48 students, 334 interactions). — Side effect of the mandated backup method; no data changed.
- D11 (pre-registered before running T1) Gate M uses the WORSE of two violation rates: (A) validation prefixes scored on the actual next skill (the brief's sample) and (B) the same prefixes scored on the 10 quiz topics (the topics the profile is actually computed for). — Safest choice: the profile is only trusted if the ordering holds both in-distribution and on the quiz topics.
- D12 Evaluation scripts import the service with a throw-away temp DB/log (scripts/_common.py) so they never touch the real DB.
- D13 Fallback (evidence-only) accuracy cut-offs 0.67 and 0.34 are treated as 2/3 and 1/3 inclusive (implemented as >= 0.665 and <= 0.34). — With 3 answers, 2 correct = 0.6667 would otherwise miss 0.67 by rounding, contrary to the evident intent.
- D14 Model policy "current level" = the topic's staircase state (`levels[topic]`, which starts at Medium and moves one step per answer from the level actually served). Candidates are that level and one step down/up; the model picks the one with predicted P closest to TARGET_P after guardrails. Ties prefer the current level, then the easier level. — Keeps the existing per-topic state and makes "one step" well-defined.
- D15 Guardrail G1 ("two consecutive wrong answers on the topic force one step down") restricts the choice to one level below the last served level on that topic. G2 removes Hard unless the topic's most recent Medium/Hard answer was correct (so a never-tested topic cannot jump to Hard).
- D16 With POLICY=model/random the served `predicted_p` is the prediction for the level actually served (re-scored); with POLICY=staircase it is unchanged (the topic-selection score). The staircase decision object still reports all three level predictions (one extra batched call) but the level rule is untouched (verified by a byte-identical trace test against the baseline engine).
- D17 Warm-up questions (first 2) and probes stay at Medium for every policy. — The model cannot predict before 2 answers; probes must stay comparable with the graph prediction made at Medium.
- D18 core5 mode: "total_questions=16" is read as the number of questions the student sees: 14 main questions on the 5 core topics (incl. the 2 warm-ups, max 4 per topic) + 2 probes on non-core topics. — Five non-core topics always remain unasked, so this total is deterministic.
- D19 `total_questions` for full10 = 15 + min(2, topics not yet asked); it can shrink from 17 to 15 during a session as topics get covered, and is exact once probing starts. The front end falls back to 15 if absent.
- D20 Decision reasons never mention whether an answer was correct. The Hard-lock reason states the rule ("Hard unlocks after a correct Medium or Hard answer on this topic"), which, like any level change, implicitly hints at past correctness; this is accepted and documented (SHOW_ADAPTATION_TOAST comment in app.js).
- D21 Simulation: initially reduced to 75 students/policy based on a wrong timing estimate (model-load time); re-run at the default 150 (149 s). Only the 150-student results are reported.
- D22 Class overview "live" = students with source live (or NULL) that have at least one interaction, excluding EXCLUDE_STUDENT_REGEX and sim_ ids; "sample" = students with source 'sample' or a sim_ id. Uses all students with interactions (not only "completed" sessions) because adaptive sessions are never marked completed (see ARCHITECTURE_NOTES item 12). The regex's `test` part also excludes ids such as "pytest_x" or "contest"; this is documented in the pilot guide.
- D23 Seed script writes only to the DB (no JSONL events) so simulated students never enter the pilot log analysis; it refuses the real DB without --yes-real-db and was tested on a temporary copy only.
- D24 The existing dashboard matrix and both skill graphs now use the shared band thresholds (70% / 40%, previously 75% / 50%), with legends updated. — Brief requires ONE band function everywhere.
- D25 Calibration is fitted on validation half A and evaluated on held-out half B (student-level split, seed 11) rather than fitted and scored on the same data. — Avoids an optimistic before/after comparison. The model's forward pass (next-step, target-aware head) is the same head used by predict_candidates in serving.
- D26 (after the demo dry run, scripts/dry_run.py) Evidence-conflict rule added to the model-based status: if the model says Needs support but >= 75% of the student's answers on that topic were correct, the status becomes Developing; if the model says Proficient/Mastered but <= 25% were correct, it moves one level down; an evidence note explains it. — The dry run's "mixed" student answered Percents 4/4 and Percent Discount 4/4 correctly yet got "Needs support", because the KT model's estimate is dominated by the most recent answers on other topics. A label contradicting the student's own answers is a correctness bug, not a tuning choice. The cut-offs (75% / 25%) were chosen before re-running the simulation and mirror the existing one-step evidence downgrade. The simulation and gates were re-run; before/after numbers are in reports/simulation_notes.md. Gate S passed both before and after.
- D27 (after user testing) Model-policy level rules now follow the student's answers on the topic: first question on a topic is Medium; after a correct answer only {same, one harder}; after a wrong answer only {one easier, same}; two correct in a row force one step up, two wrong one step down; Hard still needs a correct Medium/Hard answer; within the allowed set the level closest to TARGET_P is chosen. — A real tester answered correctly and stayed on Easy with falling percentages and never saw Hard: with an under-confident model, "closest to 70%" always chose Easy. The simulation was re-run; Gate S, applied as pre-registered, now fails, so the demo uses the staircase.
- D28 (after user testing) Cross-session history: a new session receives the student's earlier answers (prior_history); they feed every prediction (no blind warm-up when there are >= 2 earlier answers) and each topic resumes at its earlier level. Finished adaptive sessions are now marked completed when /next reports completion; earlier finished sessions (>= 15 answers) were back-filled after a SQLite backup (scripts/backfill_completed_sessions.py). The predictor keeps the most recent 500 interactions if a history is longer. — Returning students got a blind warm-up and were missing from the Student x Skill matrix.
- D29 (after user testing) No repeated question text within a session (re-generation; the global RNG state is restored so topic/level choices are unchanged).
- D30 (dry runs) Evidence-conflict rule made cautious in both directions: if the model status and the evidence-only status differ by 2+ steps, show the evidence-only status one step down when the evidence is higher, and the evidence-only status when the evidence is lower (never above what the answers support).
- D31 (after user testing; NOT pre-registered) Optional topic selection TOPIC_SELECTION=evidence_blend: rank topics by (2*P_model + correct)/(2 + answered) on that topic. Used in the demo by Rule T (reports/DEMO_CONFIG.md) because, with the staircase, it did not lower status accuracy (51.5% -> 52.8%) and raised in-band share (32.6% -> 41.6%) in simulation. Default remains the original rule. — With the original rule the system kept re-asking topics answered correctly (the model's per-topic estimates are dominated by recent answers on any topic; reports/answer_response.md).

## v3 decisions (benchmark, sections, generator)

- D32 (v3 Stage 1) v3 work lives on branch feature/v3-benchmark; new outputs only in models_v3/, reports/v3/, data/processed_v3/. Baseline before v3: pytest 85 passed / 15 failed (the same legacy fixed-quiz failures as v2, list in tests/legacy_failures_v3.txt), Node 1/4 suites (test_v2_routes.js). "Keep all existing tests passing" is enforced as "no new failure vs that list" by scripts/run_tests_v3.py, because the 15 legacy failures pre-date v2 and fixing them would change the legacy contract.
- D33 (v3 Stage 6) Sections primary / secondary / undergraduate are defined in src/serving/sections.py (topics, grade label, difficulty parameters, topic -> ASSISTments skill mapping where a reasonable one exists; undergraduate has none). /session/start accepts an optional "section"; without it the original 10-topic session runs unchanged. Section topics use synthetic ids (10xxx/20xxx/30xxx) so they never collide with ASSISTments skill ids; the session's section is recovered from these ids after a restart (no DB schema change, set_name stays "adaptive"). Before the model sees a history, section ids are translated to the mapped ASSISTments skill and unmapped ones are dropped (serving.sections.model_items), so legacy endpoints keep working for students who used a section.
- D34 (v3 Stage 6) Grade-band split of ASSISTments skills by skill NAME (serving.sections.band_for_name): a fixed keyword list marks primary-level content (whole-number arithmetic, basic fractions and decimals, rounding/estimation, number line, divisibility/primes/LCM/GCF, perimeter, area of rectangle/triangle/parallelogram, angle types, nets, volume of rectangular prism, simple tables/patterns, order of operations on positive reals, unit conversion); every other named skill is secondary (the dataset is middle-school maths); skills without a name are unassigned. No ASSISTments skill is undergraduate level. The rule is a judgement call made once, before looking at per-band results.
- D35 (v3 Stage 6, safest option) Only "secondary" is labelled "validated on real data" (ASSISTments 2009, middle-school learners). "primary" is "transfer mode: not validated on real data" although its topics map to ASSISTments skills, because the learners in the data were not primary-age; "undergraduate" is transfer mode with no mapping. In transfer mode the session uses the staircase level rule, ranks topics by the student's own answers (evidence blend with a neutral 0.5 prior), shows and logs no model prediction (predicted_p = null) and the profile is evidence-only. A section may become validated only if Stage 7 loads a real dataset for that level.
- D36 (v3 Stage 6) Section topics have no fixed question bank, so section sessions draw every question from the parametric generator src/questions/generator.py (written in Stage 6 because sections need it; Stage 8 adds the QUESTION_SOURCE flag for the default topics, the documentation and the generator tests).
- D37 (v3 Stage 7) External data: the Eedi / NeurIPS 2020 Education Challenge archive (tasks 1-2) is publicly downloadable without login and was fetched by scripts/fetch_datasets.py (657 MB, licence terms on the challenge page apply: academic, non-commercial use; check before redistributing). All other datasets need a login or licence acceptance and are listed in docs/DATASETS_TODO.md (not downloaded on the user's behalf). Eedi learners are assigned to a section by age at their first answer (UK primary ends at age 11): < 11 primary, 11-16.5 secondary, otherwise or no date of birth excluded; a seeded sample of 3000 students per section with >= 10 answers is kept (first 200 answers). Skill = most specific subject of the question; response time / attempts / hints are not in the data and are set to neutral constants (flagged). Following the rule "validated only if a real dataset for the level was loaded", primary is now labelled "validated on real data". Because that validation used a model trained on Eedi, not the served ASSISTments model, the label and the app behaviour are separated: sections.py "serving" = model only for secondary; primary stays evidence-only (no model numbers shown). Undergraduate stays transfer mode.
- D38 (v3 follow-up, user request "validate/train for undergraduate") Statics2011 (CMU OLI Engineering Statics, university learners) is obtained from the public mirror in the DKVMN authors' GitHub repository (no login; the repository has no licence file and the original PSLC DataShop terms apply, so academic use only and check before redistributing). All 333 students are assigned to undergraduate; first 500 answers each; skill from the mirror's question->skill map; no response time / attempts / hints (neutral, flagged). Same protocol as Eedi (seeded 80/10/10 split, train-only buckets, 3 seeds, 5 epochs); seed-0 deep models are saved to models_v3/ (statics2011_undergraduate_<model>_seed0.pt). Following the rule used for primary (D37), undergraduate is now labelled "validated on real data" with a note that the subject is engineering statics, not the app's maths topics. Serving stays evidence-only: the Statics-trained model cannot score the app's calculus / matrix / probability / discrete-maths items (no shared skills), so no model numbers are shown for this section.
- D39 (v3 follow-up, user request) One teacher dashboard view per learner level: tabs Default / Primary / Secondary / Undergraduate on dashboard.html (direct link dashboard.html?section=<level>). GET /class/overview takes an optional section; a level view lists only students who answered that level's topics and only those topics, with the level's validation label and serving mode. Without a section the original overview is returned unchanged. The ASSISTments mastery matrix is hidden in level views because it covers only the original topics.

# Limitations

1. **Tiny evidence per topic.** A session has 14-17 questions over 5-10 topics, so 1-4 answers per topic. Statuses and "ready" flags rest on very little data. In simulation, exact status accuracy was only about 38-42% (within one step about 83-85%), and only 40-47% of the 10 topics reached the minimum of 2 answers (reports/simulation.md). Even simulated *strong* students are often labelled "Needs support" in the seeded demo data, because the model's per-topic estimates stay low after so few answers.
2. **Synthetic evaluation.** The policy comparison uses synthetic students whose answers follow a simple logistic ability model, not the model's training distribution. It validates the decision logic (which levels get served, how statuses are assigned), not real learning and not knowledge-tracing accuracy. The demo combination (model policy + calibration + core5) was checked end-to-end but not re-simulated as a combination.
3. **Domain shift (ASSISTments 2009 -> generated quiz).** The model was trained on ASSISTments problems; the quiz uses procedurally generated template questions mapped to the same skill ids. Template Easy/Medium/Hard only approximate the data-derived difficulty buckets (per-skill tertiles of training success). Calibration and monotonicity were measured on ASSISTments validation data, not on quiz answers.
4. **Thresholds are design choices.** T_PROF = 0.70, T_READY = 0.60, MIN_ANSWERS = 2, TARGET_P = 0.70 and the target band 0.55-0.85 are reasonable conventions, not values fitted to outcomes. They are configurable (policy_config.py) and were not tuned after seeing results.
5. **No learning-outcome or teacher study.** Nothing here shows that students learn more or that teachers act better. There is no real pilot data yet (reports/pilot.md: 26 usable answers, "not meaningful yet"). No teacher has been interviewed.
6. **Small model gain.** The gated model beats DKT-only by +0.0035 validation AUC (0.8950 vs 0.8915, mean of 3 seeds); the graph alone did not help (0.8900).
7. **Design interaction.** Topic selection always picks the lowest predicted success at each topic's current level. With the staircase this means topics that drop to Easy are rarely revisited (the staircase served Easy only 2% of the time in simulation). With the model policy, low predictions for the synthetic students led to Easy 64% of the time. Real-student behaviour is unknown.
8. **Session-only history for question selection.** The predictor used to pick questions sees only the current session's answers; the profile uses the cumulative history across sessions (pre-existing design). A pending question is lost if the service restarts mid-question.
9. **Adaptive sessions are not marked "completed"** in the database (pre-existing), so the legacy "completed sessions" counters and the legacy dashboard matrix only include legacy fixed-quiz sessions; the new class overview uses all students with answers instead.
10. **Exclusion by id pattern.** Analytics exclude ids matching `(smoke|e2e|pred_check|test|^sim_)`. This also excludes real ids that contain "test" (e.g. "contest"), and it cannot catch test accounts with other names: the existing live DB contains developer accounts such as `10`, `demo_student_qa` and `dash_st_*` that are not excluded.
11. **Legacy tests.** 15 pytest tests and 3 Node smoke suites written for the old fixed 10-question flow failed before this work and still fail; they were not rewritten.
12. **Privacy.** Student ids are free text; there is no authentication. Use pseudonymous ids (docs/PILOT_GUIDE.md).

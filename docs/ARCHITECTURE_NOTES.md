# Architecture notes (verified from code, T0)

1. `src/serving/adaptive_session.py`: 10 topics (raw skill ids 204, 203, 217, 346, 371, 350, 378, 50, 48, 27); constants MAIN_QUESTIONS=15, WARMUP_QUESTIONS=2, MAX_PER_TOPIC=3, MAX_CONSECUTIVE=2, PROBE_QUESTIONS=2 — all confirmed.
2. Warm-up (first 2 questions): random never-asked topic, level "medium", `predicted_p=None`.
3. Topic choice after warm-up: among topics with count < 3 (and not the topic of the last two questions if both were the same), score `(topic, bucket_of_current_level)` with the predictor and take the **lowest** predicted P(correct).
4. Level rule: per-topic staircase starting at medium; correct -> one step up, wrong -> one step down, clamped. It reacts only to the actual answer, never to the prediction.
5. After 15 main questions: up to 2 probe questions on never-asked topics (random sample), at medium, with a predicted_p if history >= 2. Then `/next` returns `is_complete` plus graph-based `unasked_predictions` (bucket 2 = medium) for the still-unasked topics.
6. `next_question` builds a `pending` dict that holds `correct_answer` **in memory only**; `record_answer` checks it (`_check_answer`: string match or |float diff| <= 0.01), appends an interaction, and the manager stores it in SQLite (`record_adaptive_interaction`, which also saves correct_answer) and logs a JSONL "answer" event. The "question" event is logged in `AdaptiveSessionManager.next_question` (no student_id key).
7. `from_history` rebuilds a session by replaying **only that session's** interactions (`get_session_interactions`). Therefore the predictor used for topic choice during a session sees **only the current session's history**, while `/session/{id}/predict` and `/student/{id}/*` use the cumulative history across all of the student's sessions (`get_full_history`). A pending question is lost if the service restarts.
8. `inference_service._predictor(history, [(raw_skill_id, bucket)])` -> list of P(correct) using `model.predict_candidates` (difficulty-aware via `diff_emb`); unknown skills get 0.5.
9. Difficulty buckets (`dataset.derive_difficulty`): per skill, problems with >= 5 train responses are tertiled by train mean correctness: 1 = easy (highest success), 2 = medium, 3 = hard; **0 = unknown** (too few samples, or < 3 reliable problems in the skill). `LEVEL_TO_BUCKET = {easy:1, medium:2, hard:3}`; template levels only approximate these data-derived buckets.
10. `_process_history` (used by /predict, /session/{id}/predict, /student/{id}/predict, trend, matrix, subgraph) fills skills not observed as a next-step target with bucket 0 (unknown) candidates.
11. Endpoints: /health, /skills, /predict, /predict_batch, /session/start, /session/{id}/next, /answer, /history, /predict, /gate, /gate_detail, /gate_plot.png, /student/{id}/summary|predict|trend, /students/matrix, /graph/subgraph. Node proxy (`server/src/index.js`) maps `/api/*` to these plus local /api/skills, /api/sample_students, /api/dashboard/matrix.
12. Adaptive sessions are **never marked completed** (`complete_session` is only called by the legacy fixed-quiz SessionManager), so the legacy "completed sessions" counters and /students/matrix do not include adaptive sessions.
13. DB: SQLite `data/processed/kt_sessions.db` (WAL); `students.source` in {live, sample, test}. Event log `data/processed/session_logs.jsonl` with "question"/"answer" events.
14. Served checkpoint `best_full_gated.pt` is byte-identical to `best_full_gated_seed42.pt` (md5 a3d279d3...). Reported val AUC over 3 seeds (retrain.log): dkt_only 0.8915, graph_no_gate 0.8900, full_gated 0.8950 (gate +0.0035 over DKT; the graph alone did not help).
15. Front end: `server/public/app.js` (renderQuestion, finishQuiz, renderMasteryBars, renderUnaskedPredictions, renderSkillGraph, renderMasteryTrend, renderGateDynamics); no correct/incorrect verdict is shown during the quiz. Chart.js and vis-network load from CDNs (unversioned URLs). The Node smoke tests `test_frontend_smoke.js` and `test_dashboard_smoke.js` still drive the legacy fixed 10-question `/answer` flow.
